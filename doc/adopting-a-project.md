# 기존 프로젝트 읽어오기 — `rescue` 레이아웃 실제 기록

> [문서 목록으로](../readme.md)

---

이 문서는 **이미 다른 방식으로 만들어져 운영 중인 게임의 엑셀 17개를 그대로 읽어본 기록**입니다. 무엇을 어떻게 설정했고, 무엇이 걸렸고, 무엇을 원본에 돌려보냈는지까지 적습니다.

[시트 작성](sheets.md#다른-레이아웃-읽기--rescue)이 `rescue` 레이아웃의 **규칙**이라면, 이 문서는 그 규칙을 실제 프로젝트에 적용한 **사례**입니다. 비슷한 상황이라면 이 순서대로 하면 됩니다.

## 상황

그 프로젝트는 구글 스프레드시트를 CSV로 내려받아 유니티 에디터 툴로 C# 클래스를 만들어 쓰고 있었습니다. 시트는 이렇게 생겼습니다.

```
row 1   필드 설명(한글)     ← `#`으로 시작하면 그 컬럼은 빠짐
row 2   필드 이름           ← 첫 컬럼이 인덱스
row 3   필드 타입           ← Int / int / IntArray / enum:GradeType ...
row 4~  데이터
```

마커가 없고, **시트 탭 이름이 곧 테이블 이름**입니다. enum은 `TableEnums`라는 시트 하나에 컬럼 단위로 모여 있고, 값 없이 라벨 이름만 적혀 있습니다.

우리 레이아웃과 겹치는 게 거의 없어서, 워크북을 먼저 고쳐 쓰는 대신 **읽는 쪽을 하나 더 만드는 편이 쌌습니다.** 그게 `rescue` 레이아웃입니다.

## 1. 읽을 시트를 정한다

가장 먼저 한 일은 변환이 아니라 **목록 만들기**였습니다.

워크북 17개에 시트가 85장 있는데, 그중 게임이 실제로 쓰는 건 일부입니다. 나머지는 참고용 탭, 기획 메모, 만들다 만 표, 다른 팀이 쓰는 시트입니다. 무엇이 진짜인지는 시트를 봐서는 알 수 없고 — **클라이언트가 다운로드 대상으로 등록해둔 목록**에 적혀 있었습니다.

그 목록을 그대로 `IncludeSheets`에 옮겼습니다.

```jsonc
{
  "Sources": {
    "Xlsx": [{
      "Path": "project-rescue-xlsxs",
      "FileExtensionPatterns": ".xlsx",
      "Layout": "rescue",

      "IncludeSheets": [
        "TableEnums",          // enum 모음. 아래 모든 enum: 컬럼이 여기를 봅니다

        "CurrencyTable", "MaterialTable", "PackageTable", "EquipTable",
        "CharacterTable", "SkillTable", "ArtifactTable", "StageTable",
        "SDAgencyTable", "GoldDungeonStageTable", "StatGrowthTable"
        // ... 실제로는 68개
      ]
    }]
  }
}
```

**적어놓고 없는 시트는 오류입니다.** 이게 목록으로 관리하는 이유입니다 — 시트 이름이 바뀌면 조용히 빠지는 게 아니라 변환이 멈추고, 실제로 있는 시트 목록을 같이 보여줍니다.

전체는 [project-rescue-xlsxs/recipe.jsonc](../project-rescue-xlsxs/recipe.jsonc)에 있습니다.

> **골라내는 순간 범위가 확 줄어듭니다.** 85장 전부를 읽으려 했을 때는 관용 규칙이 넷 필요했는데, 실제로 쓰는 68장으로 좁히자 **셋이 필요 없어졌습니다.** 미정의 enum도, `none`이 든 숫자 컬럼도, 정의에 없는 라벨도 전부 등록되지 않은 시트에만 있었기 때문입니다.

## 2. 걸리는 것을 하나씩 본다

첫 변환은 실패합니다. 그게 정상입니다 — 수년 묵은 데이터에는 사람이 저지른 것이 쌓여 있고, 그걸 드러내는 게 이 도구의 일입니다.

68장에서 걸린 것은 넷이었습니다.

|무엇|어디|어떻게 했나|
|--|--|--|
|Id가 56행 중복|`ArtifactLevelTable`|**원본 오류.** 수식 복사 사고로 레벨 46~101 행의 Id가 전부 45. 제작사에 알리고, 그동안은 `OnDuplicateIndex: keep-first`|
|Id 칸이 빈 행 9개|`SkillTable`|작성 중인 행. 규칙으로 건너뛰고 경고|
|Id가 `#9`, `#10`인 행 2개|`CollectionGroupTable`|행 주석. 규칙으로 건너뜀|
|첫 컬럼이 `string`|`ConfigTable`|순번 `Index` 컬럼을 앞에 만들고, 원래 `Id`는 보조 인덱스로|

앞의 셋은 `rescue` 레이아웃의 **규칙**으로 처리됩니다 — recipe에 아무것도 안 적어도 그렇게 동작합니다. 넷째도 마찬가지고, 결과적으로 `FindByIndex(int)`와 `FindById(string)` 둘 다 나옵니다.

**설정이 필요한 건 첫 줄 하나뿐이었습니다.**

```jsonc
// ArtifactLevelTable 48~104행의 Id가 전부 45입니다. 원본 스프레드시트의
// 복사 사고이고 이 도구가 풀 수 있는 문제가 아닙니다 — 레벨 46~101은
// 어느 쪽으로 처리해도 도달할 수 없습니다. 고쳐질 때까지 나머지를 돌리기
// 위한 것이고, 버린 행은 전부 로그에 남습니다. 고쳐지면 `error`로 되돌리세요.
"OnDuplicateIndex": "keep-first"
```

> **관용 설정에는 왜 켰는지와 언제 끌지를 같이 적으세요.** 이런 설정은 켠 사람이 회사를 떠난 뒤에도 남아 있습니다.

## 3. 변환하고, 확인한다

```
sheetman --recipe project-rescue-xlsxs/recipe.jsonc
```

68장에서 **테이블 67개, enum 37개, 103,395행**이 나왔습니다. 산출물은 [project-rescue-xlsxs/out/](../project-rescue-xlsxs/out/)에 있고, 13개 언어 코드와 바이너리·JSON·HTML 문서가 전부 들어 있습니다.

확인은 눈으로 하지 말고 도구로 하세요.

- **HTML 문서**를 열면 실제로 로드된 값이 표로 나옵니다. 숫자가 이상한 컬럼은 여기서 보입니다.
- **생성된 코드를 컴파일해 보세요.** 이 사례에서는 C# 107개 파일이 경고 없이 컴파일됐습니다.
- **바이너리를 되읽어 보세요.** 값이 왕복하는지가 마지막 확인입니다.

## 4. 원본에 돌려보낼 것을 정리한다

변환기가 잡아낸 것 중 **데이터 자체의 문제**는 고쳐서 쓰는 게 아니라 원본에 돌려보내야 합니다. 이 사례에서는 별도 보고서로 정리했습니다 — 무엇이 지금 문제이고 무엇이 아직 안 쓰이는 시트라 잠복 상태인지 구분해서.

여기서 배운 것 하나: **「지금 문제」와 「잠복」을 구분해서 알려주면 상대가 우선순위를 정할 수 있습니다.** 등록 목록과 대조하면 그 구분이 바로 나옵니다.

## 옮겨갈 때

`rescue`는 **머무는 곳이 아니라 지나가는 곳**입니다. 최종적으로는 우리 레이아웃으로 옮기는 편이 낫습니다 — `foreign` 참조도, 서버/클라 분리도, 와이어 태그도 `rescue`에는 없습니다.

한꺼번에 옮길 필요는 없습니다. **소스 항목마다 레이아웃을 따로 주면 되므로**, 옮긴 워크북과 아직 안 옮긴 워크북을 한 recipe에서 같이 읽을 수 있습니다.

```jsonc
"Xlsx": [
  { "Path": "./sheets",        "Layout": "sheetman" },
  { "Path": "./legacy-sheets", "Layout": "rescue"   }
]
```

enum 선언은 레이아웃을 가로질러 해석되므로, 한쪽에서 선언한 enum을 다른 쪽 테이블이 타입으로 써도 됩니다. 옮기는 도중을 위한 것이라 그렇게 만들었습니다.

### 옮기기 전에 알아둘 것

- **이름 정규화는 양쪽이 같습니다.** `STAR_LEVEL`은 `STARLEVEL`이 되고, `Icon_Path`와 `IconPath`는 같은 이름으로 충돌해 오류가 납니다. 후자는 실제로 겪었고, 그대로 두면 snake_case 언어에서 13번 서로 다르게 터지므로 여기서 잡는 게 맞습니다. 데이터 셀은 원문(`STAR_LEVEL`)으로 그대로 매칭되니 시트는 고치지 않아도 됩니다.
- **연속 번호 컬럼은 `rescue`에서 묶이지 않습니다.** 그쪽엔 그 관례가 없어서 숫자는 그냥 이름의 일부입니다. 옮기고 나면 `Reward1`~`Reward5`가 배열이 되므로, 그때 읽는 코드가 바뀝니다.
- **enum 값은 등장 순서로 매겨집니다.** `rescue` 시트에 값이 안 적혀 있기 때문입니다. 내부적으로 일관되면 되지만, **라벨을 지우거나 순서를 바꾸면 이미 내보낸 데이터의 의미가 바뀝니다.** 옮길 때 값을 명시적으로 적어두는 게 좋습니다.
