# 다른 규칙으로 쓰인 시트 읽기 — `rescue` 적용 기록

> [문서 목록으로](../readme.md)

---

다른 규칙으로 작성된 게임 데이터 시트 한 벌을 `rescue` 레이아웃으로 읽은 기록입니다. 무엇을 설정했고 무엇이 걸렸는지를 순서대로 적고, **레이아웃의 규칙도 여기 함께** 두었습니다.

`rescue`는 **시트를 고치지 않고 그대로 읽기 위한** 레이아웃입니다. 여기서 나오는 코드·바이너리·문서는 `sheetman` 레이아웃과 동일합니다.

```jsonc
"Xlsx": [{ "Path": "./other-sheets", "Layout": "rescue" }]
```

## 시트의 모양

구글 스프레드시트로 작성되어 있고, 유니티 에디터 툴이 CSV로 내려받아 C# 클래스를 만들어 쓰는 구조였습니다. 마커가 없고 **시트 탭 이름이 곧 테이블 이름**이며, 머리 3줄 다음이 데이터입니다.

```
row 1   필드 설명       ← `#`으로 시작하면 그 컬럼은 빠짐
row 2   필드 이름       ← 첫 컬럼이 인덱스
row 3   필드 타입       ← Int / int / IntArray / enum:GradeType ...
row 4~  데이터
```

enum은 **이름에 `TableEnums`가 들어간 시트** 하나에 컬럼 단위로 모입니다. 값을 적는 칸은 없습니다.

```
row 1   enum 설명       ← `#`이면 왼쪽 enum의 라벨 설명 컬럼
row 2   enum 이름
row 3~  라벨            ← 값은 안 적음. 등장 순서대로 매겨짐
```

`sheetman` 기본 레이아웃과 겹치는 부분이 거의 없어, 시트를 고치는 대신 읽는 쪽을 하나 더 만들었습니다.

## `sheetman`과 무엇이 다른가

|                | `sheetman` | `rescue` |
|--|--|--|
|엔티티 위치|마커로 선언, 한 시트에 여러 개|시트 하나 = 테이블 하나|
|테이블 이름|마커에 적음|시트 탭 이름에서 끝의 `Table`을 뗀 것|
|타입 표기|`int` `int[]` + detail-type 칸에 enum 이름|`Int` `intArray` `enum:GradeType` (대소문자 무관)|
|`bigint`|`bigint`|`long`|
|배열 셀 구분자|recipe의 `ArrayDelimiter` (기본 `;`)|같음. 소스 항목마다 다르게 줄 수 있습니다|
|`TargetSide`|컬럼마다 지정 가능|없음 (전부 `cs`)|
|`foreign` 참조|지원|없음|
|`@N` 와이어 태그|지원|없음 (순번 모드)|
|`*` 보조 인덱스|지원|없음 (첫 컬럼만)|
|연속 번호 컬럼|`Text1` `Text2` → 배열로 묶음|**묶지 않음**|

연속 번호를 묶지 않는 것은 `rescue`에 그런 관례가 없어서 숫자가 이름의 일부이기 때문입니다. 실제로 한 테이블의 `Condition_1` `Condition_2` `Condition_3`이 서로 다른 enum이라, 묶으면 타입 불일치로 변환이 멈춥니다. **`rescue`에서 배열은 한 셀 안에 구분자로 이어 적은 것뿐입니다.**

표의 아래쪽 다섯은 **SheetMan이 자체 레이아웃에 정의한 표기**이고 시트에 적을 자리가 없으므로 나오지 않습니다. 그 점을 빼면 `rescue`로 읽은 결과는 `sheetman`으로 읽은 것과 동일한 자격을 가집니다 — 같은 코드, 같은 바이너리, 같은 문서, 같은 검증.

enum 값은 라벨이 등장한 순서로 매겨집니다. 시트에 값을 적는 칸이 없기 때문입니다. 내부적으로는 일관되지만, **라벨을 지우거나 순서를 바꾸면 이미 내보낸 데이터의 의미가 바뀝니다.** 라벨은 뒤에 붙이는 편이 안전합니다.

## 관용 규칙

`rescue` 레이아웃에서만 적용됩니다. `sheetman` 쪽은 그대로입니다.

|상황|처리|
|--|--|
|탭 이름이 `Table`로 끝남|테이블 이름에서 떼고 읽음. 코드 생성기가 컨테이너 타입 이름에 `Table`을 다시 붙이므로, 그대로 두면 `ItemTableTable` 같은 클래스가 나옵니다. 탭 이름이 `Table` 하나뿐이면 그대로 둡니다|
|인덱스 셀이 `#`/`//`로 시작|주석 처리된 행으로 보고 건너뜀|
|인덱스 셀은 비었는데 다른 칸에 내용|작성 중인 행으로 보고 건너뛰고 **경고**|
|첫 컬럼이 `int`가 아님|순번 `Index` 컬럼을 앞에 만들어 기본 인덱스로 삼고, 원래 컬럼은 **보조 인덱스로 유지**. 시트가 쓰던 키로 계속 조회됩니다|
|인덱스 값 중복|기본은 오류. recipe의 `OnDuplicateIndex`로 `keep-first`/`keep-last` 선택 가능|

`OnDuplicateIndex`의 기본값이 `error`인 것은 인덱스의 정의 자체가 유일성이기 때문입니다. 나머지 둘은 원본을 고칠 수 없는 동안 나머지를 변환하기 위한 것이고, 버린 행은 전부 로그에 남습니다.

**테이블인지 아닌지는 시트가 말해주지 않습니다.** 참고용 탭이 데이터 옆에 섞여 있으므로 3행 첫 칸이 인식 가능한 타입인지로 판정하고, 아니면 건너뛰며 로그에 남깁니다. 확실히 하려면 `IncludeSheets`에 읽을 시트를 적으세요 — 그러면 적었는데 없는 시트가 오류로 잡힙니다. 다음이 그 이야기입니다.

## 1. 읽을 시트를 정한다

워크북 17개에 시트가 85장 있고, 그중 게임이 실제로 쓰는 것은 일부입니다. 나머지는 참고용 탭, 작업 메모, 작성 중인 표입니다. 어느 쪽인지는 시트만 봐서는 알 수 없고, **클라이언트가 다운로드 대상으로 등록해둔 목록**에 68장이 적혀 있었습니다.

그 목록을 `IncludeSheets`에 옮겼습니다.

```jsonc
{
  "Sources": {
    "Xlsx": [{
      "Path": "samples/rescue",
      "FileExtensionPatterns": ".xlsx",
      "Layout": "rescue",

      "IncludeSheets": [
        "TableEnums",          // enum 모음. 모든 enum: 컬럼이 여기를 봅니다

        "CurrencyTable", "MaterialTable", "PackageTable", "EquipTable",
        "CharacterTable", "SkillTable", "ArtifactTable", "StageTable",
        "SDAgencyTable", "GoldDungeonStageTable", "StatGrowthTable"
        // ... 전체 68개
      ]
    }]
  }
}
```

적어놓고 없는 시트는 오류입니다 — 시트 이름이 바뀌면 조용히 빠지지 않고 변환이 멈추며, 실제로 있는 시트 목록을 함께 보여줍니다. 전체는 [samples/rescue/recipe.jsonc](../samples/rescue/recipe.jsonc)에 있습니다.

> 범위를 좁힌 효과가 큽니다. 85장 전부를 대상으로 했을 때는 관용 규칙이 넷 필요했는데, 68장으로 좁히자 셋이 필요 없어졌습니다. 미정의 enum, `none`이 든 숫자 컬럼, 정의에 없는 라벨이 전부 등록되지 않은 시트에만 있었습니다.

## 2. 걸린 것

68장에서 넷이 걸렸습니다.

|무엇|어디|처리|
|--|--|--|
|Id가 56행 중복|`ArtifactLevelTable`|원본의 값 문제. `OnDuplicateIndex: keep-first`로 우회하고 원본에 보고|
|Id 칸이 빈 행 9개|`SkillTable`|작성 중인 행. 규칙으로 건너뛰고 경고|
|Id가 `#9`, `#10`인 행 2개|`CollectionGroupTable`|행 주석. 규칙으로 건너뜀|
|첫 컬럼이 `string`|`ConfigTable`|순번 `Index` 컬럼을 앞에 만들고 원래 `Id`는 보조 인덱스로|

넷 중 셋은 `rescue` 레이아웃의 기본 규칙으로 처리됩니다. 넷째도 마찬가지이고, 결과적으로 `FindByIndex(int)`와 `FindById(string)`이 둘 다 나옵니다.

recipe에 추가한 설정은 한 줄뿐이었습니다.

```jsonc
// ArtifactLevelTable 48~104행의 Id가 전부 45입니다. 원본 스프레드시트의
// 값 문제이고, 어느 쪽으로 처리해도 레벨 46~101에는 도달할 수 없습니다.
// 고쳐질 때까지 나머지를 변환하기 위한 설정이며, 버린 행은 전부 로그에
// 남습니다. 원본이 고쳐지면 `error`로 되돌리세요.
"OnDuplicateIndex": "keep-first"
```

> 관용 설정에는 왜 켰는지와 언제 끌지를 같이 적어두는 편이 낫습니다. 그래야 나중에 지울 수 있습니다.

## 3. 변환과 확인

```
sheetman --recipe samples/rescue/recipe.jsonc
```

68장에서 **테이블 67개, enum 37개, 103,395행**이 나왔습니다. 산출물은 [samples/rescue/out/](../samples/rescue/out/)에 있고, 13개 언어 코드와 바이너리·JSON·HTML 문서가 들어 있습니다.

확인한 방법은 셋입니다.

- **HTML 문서.** 실제로 로드된 값이 표로 나오므로 값이 이상한 컬럼이 눈에 띕니다.
- **생성 코드 컴파일.** C# 107개 파일이 경고 없이 컴파일됐습니다.
- **바이너리 되읽기.** 값이 왕복하는지 확인했습니다.

## 4. 원본에 돌려보낼 것

변환기가 잡아낸 것 중 데이터 자체의 문제는 [별도 보고서](../samples/rescue/데이터-이슈-보고-20260807.md)로 정리했습니다. 등록 목록과 대조하면 **지금 쓰이고 있어 문제가 되는 것**과 **아직 안 쓰이는 시트에 있는 것**이 구분되므로, 그 구분을 붙여서 전달했습니다.

## 두 레이아웃을 같이 쓰기

레이아웃은 소스 항목마다 지정하므로 한 recipe에서 같이 읽을 수 있습니다. enum 선언은 레이아웃을 가로질러 해석되므로, 한쪽에서 선언한 enum을 다른 쪽 테이블이 타입으로 써도 됩니다.

배열 구분자가 서로 다르면 소스 항목에 `ArrayDelimiter`를 적습니다. recipe 전체 설정보다 항목 쪽이 우선합니다.

```jsonc
"Xlsx": [
  { "Path": "./sheets",       "Layout": "sheetman" },
  { "Path": "./other-sheets", "Layout": "rescue", "ArrayDelimiter": "|" }
]
```

> 레이아웃 하나가 더 준비 중입니다. 라이브 서비스 중인 프로젝트의 것이고, 정의된 이름으로 테이블 경계를 잡고 컬럼 이름으로 중첩 구조를 만듭니다 — 규격과 우리에게 없는 것은 [uwo 레이아웃 분석](uwo-레이아웃-분석-20260808.md)에 있습니다.

이름 정규화는 양쪽이 같습니다. `STAR_LEVEL`은 `STARLEVEL`이 되고, `Icon_Path`와 `IconPath`는 같은 이름으로 충돌해 오류가 납니다. 그대로 두면 snake_case 언어에서 13번 서로 다르게 깨지므로 변환 단계에서 잡습니다. 데이터 셀은 원문(`STAR_LEVEL`)으로 매칭되므로 시트는 고치지 않아도 됩니다.

## 원 파이프라인에 드리는 개선 권고

원 파이프라인은 시트 내려받기부터 클래스 생성, 로드까지 툴 하나로 해결하는 간결한 구조이고, 지금까지 프로젝트를 잘 지탱해 왔습니다. 데이터 자체의 이슈는 §4의 보고서로 전달했으므로, 여기서는 함께 읽는 동안 눈에 띈 **파이프라인 차원에서 보완하면 좋을 지점**만 따로 정리합니다. 대부분 지금 당장의 문제라기보다 데이터가 늘었을 때를 대비하는 것들이고, 우선순위는 팀의 판단에 맡깁니다.

**1. Id 중복이 조용히 지나갑니다.** 로드가 `targetDict[id] = data` 형태라 같은 Id가 다시 나오면 예외도 로그도 없이 앞 행이 덮입니다. 이번에 실제로 한 테이블이 이 경로로 다른 행의 값을 갖게 된 상태였습니다 (보고서 1번). 담기 전에 `ContainsKey`를 한 번 보거나 `Add()`로 바꾸면, 이 문제가 조회 시점이 아니라 로드 시점에 로그 한 줄로 드러납니다. 고치는 양에 비해 얻는 것이 가장 큰 항목이라 생각합니다.

**2. 유실된 행의 집계가 있으면 좋겠습니다.** 파싱에 실패한 행은 행마다 `Debug.LogError`가 남으니 조용하지는 않습니다. 다만 빌드도 로드도 계속 진행되고, 로드 시점에 쏟아지는 다른 로그에 섞이면 찾아보기 전에는 알기 어렵습니다. 로드가 끝난 뒤 시트별로 「전체 N행 / 유실 M행」 한 줄만 집계해도, 유실이 있다는 사실 자체는 놓치지 않게 됩니다.

**3. 검증 시점을 앞당길 수 있습니다.** 지금은 시트의 문제가 게임을 실행해 그 테이블을 로드할 때 처음 드러나므로, 시트를 고친 시점과 문제를 발견하는 시점이 멀어집니다. 내려받기 단계가 이미 에디터 툴에 있으니, 내려받은 직후 전 시트를 한 번 파싱해 보는 검사만 붙여도 시트를 고친 사람이 그 자리에서 결과를 볼 수 있습니다.

**4. CSV를 `Split(',')`으로 나누고 있습니다.** 따옴표를 해석하지 않으므로, 셀 안에 쉼표가 들어가면 그 뒤 컬럼이 전부 한 칸씩 밀립니다. 지금 데이터의 쉼표는 전부 마지막 컬럼이거나 제외된 컬럼에 있어 무해하지만, 중간의 숫자 컬럼끼리 밀리면 오류 없이 잘못된 값이 들어갈 수 있습니다 (보고서 11번). 따옴표를 이해하는 CSV 파서로 바꾸거나 탭 구분(TSV)으로 받는 것을 권합니다.

**5. enum 라벨 매칭이 표기에 엄격합니다.** `Enum.Parse`가 대소문자를 구분하므로 `Monster`(정의는 `MONSTER`) 같은 표기 차이가 그대로 행 유실로 이어집니다. 파싱 쪽은 `ignoreCase: true` 인자 하나로 충분하고, 시트 쪽에는 데이터 검증(드롭다운)을 걸어두면 입력 시점에 막을 수 있습니다.

**6. enum 값이 라벨 순서에 매여 있습니다.** 시트에 값을 적는 칸이 없어 생성 코드의 값이 등장 순서로 정해집니다. 저장 데이터나 통신에 정수 값이 실린 뒤에는 라벨을 지우거나 순서를 바꾸는 것이 기존 값의 의미를 바꾸므로, 「라벨은 끝에만 추가」 관례를 문서로 못박아 두거나 값 컬럼 도입을 고려해 보시면 좋겠습니다. 같은 제약은 이 시트를 `rescue` 레이아웃으로 읽을 때도 그대로 적용되어, 위에서 저희 쪽 사용자에게 한 주의와 같은 이야기입니다.

**7. 시트의 성격이 겉으로 드러나지 않습니다.** 탭 이름만으로는 게임이 쓰는 시트인지 참고용인지 알 수 없고, 등록 목록과 대조해야 합니다. 행·컬럼에는 이미 `#` 관례가 있으니 참고용 탭 이름에도 같은 접두를 쓰기로 하면, 목록을 열지 않고도 시트 안에서 구분이 됩니다.

일곱 가지 모두 구조를 바꾸는 이야기가 아니라 지금 구조에 안전장치를 더하는 이야기입니다. 굳이 순서를 고르자면 1번이 먼저입니다 — 유일하게 로그 없이 값이 달라지는 경로이기 때문입니다.
