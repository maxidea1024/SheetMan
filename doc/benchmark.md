# 벤치마크 — JSON, compact JSON, 바이너리

> [문서 목록으로](../readme.md)

[내보내기](exports.md#왜-바이너리인가)가 바이너리를 쓰는 이유를 말로 설명한다면, 이 문서는 그 차이를 숫자로 잽니다. 같은 게임 데이터를 세 형식으로 내보내고, 각각을 런타임이 하는 방식 그대로 실어서 파일 크기·로드 시간·CPU·메모리를 측정했습니다.

## 데이터셋

실제 모바일 게임의 기획 데이터입니다 — [rescue 레이아웃](adopting-a-project.md)으로 변환한 상용 프로젝트 워크북 그대로, **67개 테이블 · 109,218행**. 합성 데이터가 아니므로 실제 게임 데이터가 가진 모양이 그대로 들어 있습니다: 수십 행짜리 설정 테이블부터 103,395행 × 9컬럼짜리 성장 수치 테이블(`StatGrowth`)까지, 문자열 경로·enum·가변 배열·64비트 정수가 섞여 있습니다.

세 형식은 **한 번의 변환에서** 나옵니다([bench/recipe.jsonc](../bench/recipe.jsonc)). 그래서 내용이 다를 수가 없고, 그 사실을 하네스의 `verify` 모드가 믿음이 아니라 값으로 확인합니다 — 세 경로로 로드한 결과를 테이블마다 표본 행에서 필드 단위로 대조합니다.

|형식|무엇|
|--|--|
|바이너리|`.scb`, [컬럼 지향 형식](binary-format.md). 런타임 형식이므로 생성된 테이블 리더가 그대로 읽습니다. 컬럼마다 인코딩을 고르지만 범용 압축은 쓰지 않습니다|
|JSON|이름 있는 행(`{"id": 1, "name": …}`), 공백 없음|
|compact JSON|배열 행(`[1, "…", …]`), 공백 없음. recipe의 `UseCompactRowFormat`|

## 결과

Windows 11 · i5-13600KF(14코어 20스레드) · .NET 10 · 워크스테이션 GC. 로드 수치는 실행 다섯 번(각각 워밍업 1회 + 30회 반복)의 중앙값입니다.

|측정|바이너리|JSON|compact JSON|
|--|--|--|--|
|파일 크기|**0.36 MB**|20.90 MB (58배)|9.24 MB (26배)|
|파일 크기, gzip 후|**0.07 MB**|1.10 MB (16배)|0.96 MB (14배)|
|전체 로드, 벽시계|**8 ms**|60 ms (7.5배)|42 ms (5.3배)|
|전체 로드, CPU 시간|**23 ms**|98 ms (4.2배)|68 ms (2.9배)|
|로드 중 총 할당|**12.4 MB**|50.1 MB|38.3 MB|
|└ 그중 로드가 끝나면 쓰레기|**0.5 MB**|22.2 MB|10.4 MB|
|로드 후 상주 메모리|**11.9 MB**|27.9 MB|27.9 MB|

### 읽는 법

**크기 차이를 만드는 것은 바이너리라는 사실이 아니라 [컬럼 인코딩](binary-format.md#컬럼-인코딩)입니다.** 값을 그대로 나열하기만 하던 시절 이 데이터셋은 7.84 MB였고, JSON 대비 2.7배·gzip 후 1.7배였습니다 — 값 하나하나는 조밀했지만 값 **사이**의 중복을 전혀 모델링하지 않았기 때문입니다. 그 중복이 실은 파일의 대부분이었습니다: 문자열 컬럼이 69%, 그중 최대 컬럼은 서로 다른 값 3개를 103,395번 적고 있었고, 정수 컬럼은 0~750짜리 값에 4바이트씩 쓰고 있었습니다. 컬럼마다 사전·델타·런 길이 중 가장 작은 배치를 고르게 하자 7.84 MB가 **0.36 MB**가 됩니다.

**파일 크기가 곧 할당량 차이입니다.** 어느 경로든 파일 전체를 한 번 버퍼로 읽으므로, 로드가 끝나면 버려지는 쓰레기의 대부분이 그 버퍼입니다 — JSON 22.2 MB 중 20.9 MB가 그것입니다. 바이너리 쪽은 파일이 0.36 MB라 버릴 것 자체가 거의 없어 쓰레기가 0.5 MB에 그칩니다. 텍스트 형식의 부피는 전송량으로 한 번, 로드할 때 가비지로 또 한 번 청구됩니다. 모바일에서 로딩 중 프레임 끊김을 만드는 것이 이 가비지입니다.

**상주 메모리도 이제 다릅니다.** 예전에는 셋이 같았고, 그것이 맞는 설명이었습니다 — 로드가 끝나면 남는 것은 형식과 무관하게 같은 모양의 레코드 객체·문자열·인덱스 사전이었으니까요. 사전 인코딩이 그 전제를 깼습니다. 유니크 값 3개짜리 문자열 컬럼을 읽을 때 JSON 경로는 문자열 객체를 103,395개 만들고, 바이너리 경로는 사전을 한 번 풀어 **3개**를 만든 뒤 행마다 그 참조를 나눠 줍니다. 27.9 MB와 11.9 MB의 차이가 대부분 그것입니다. 파일 크기를 줄이려고 넣은 인코딩이 상주 메모리를 함께 줄인 셈인데, 이건 우연이 아니라 같은 사실의 두 얼굴입니다 — 반복되는 값은 파일에서도 힙에서도 한 번만 있으면 됩니다.

**행이 많을수록 이름 있는 JSON이 불리해집니다.** 키 문자열이 행마다 반복되기 때문입니다 — 이 데이터셋의 최대 테이블(`StatGrowth`, 103,395행)에서 JSON은 18.90 MB, 그 반복을 지운 compact JSON은 8.46 MB입니다. compact가 JSON에 대해 하는 일(반복되는 키를 한 번만 적기)을 컬럼 인코딩은 **값에 대해서도** 합니다. 그 테이블이 실제로 담고 있는 것 — id는 1씩 증가하고, 문자열 컬럼 셋은 유니크 값이 각각 165·3·3개이며, 나머지 정수 컬럼도 등차이거나 몇 값의 반복 — 을 그대로 적으면 **5.4 KB**입니다. 같은 데이터입니다. 18.90 MB가 그 안에 들어 있던 것은 값이 아니라 반복이었습니다.

**compact JSON은 생각보다 선전하지만, 남는 차이가 인코딩입니다.** 키 반복을 지우면 크기와 파싱의 상당 부분이 함께 사라집니다. 그래도 숫자는 여전히 십진 텍스트라 값마다 문자열→숫자 변환을 거치고, 토큰 하나하나(따옴표·쉼표·대괄호)를 찾는 일은 남습니다. 그 몫이 벽시계 1.8배·CPU 1.2배입니다. 그리고 compact는 **위치가 계약**입니다 — 컬럼 순서가 바뀌면 읽는 쪽 코드가 함께 바뀌어야 하고, 어긋나면 형식이 그것을 잡아주지 않습니다.

**gzip은 이제 차이를 좁히지 못합니다.** 텍스트의 반복은 압축이 잘 먹지만, 컬럼 인코딩이 이미 같은 반복을 형식 안에서 지운 뒤라 gzip에게 남은 일이 별로 없습니다 — 압축 전 58배가 압축 후에도 16배로 남습니다. **압축하지 않은 `.scb`(0.36 MB)가 gzip한 JSON(1.10 MB)보다 3배 작습니다.** 압축 라이브러리를 13개 언어에 다는 대신 형식이 스스로 해낸 결과이고, `flags` 바이트에 압축 비트를 비워 둔 채로 그렇습니다.

**CPU 시간은 벽시계보다 차이가 작습니다.** 로드가 테이블별로 병렬이라, 벽시계는 코어가 많을수록 압축되고 CPU 시간은 총 작업량을 그대로 보여줍니다. 코어가 적은 기기일수록 벽시계가 CPU 시간 쪽으로 다가간다고 읽으면 됩니다. CPU 시간은 OS가 15.625 ms 단위로 집계하므로 ±10 ms 안팎의 흔들림이 있습니다.

### 표에 없는 것

이 표는 **크기와 속도만** 잽니다. 바이너리를 쓰는 이유의 나머지 절반 — 텍스트를 거치지 않아 값이 변하지 않는다는 것, 스키마가 바뀌어도 [조용히 어긋나지 않는다](binary-format.md)는 것 — 은 벤치마크로 잴 수 있는 성질이 아니고, 세 형식 중 바이너리만 가집니다.

## 측정 방법

하네스는 [bench/](../bench/readme.md)에 있고, 공정성 규칙은 이렇습니다.

- **바이너리**는 생성된 테이블 리더의 `ReadAllAsync` 그대로입니다 — 파일별 병렬 읽기, 인덱스 사전 구성, 상호참조 연결까지.
- **JSON 두 형식**은 생성된 리더가 없으므로(그것이 없다는 것 자체가 JSON을 싣는 팀의 조건입니다), 그런 팀이 썼을 코드를 하네스가 대신 씁니다: 테이블마다 타입이 정확한 DTO, `System.Text.Json` 역직렬화(compact는 위치 기반 `Utf8JsonReader` 루프), 그리고 바이너리 쪽과 같은 인덱스 사전 구성. 파일별 병렬 구조도 같습니다.
- DTO 타입 생성과 컴파일된 세터 준비는 측정 밖입니다 — JSON을 싣는 프로젝트라면 컴파일 타임에 있었을 코드이므로.
- 파서 선택은 JSON에 유리한 쪽입니다. `System.Text.Json`은 주류 .NET JSON 파서 중 가장 빠르고 할당이 적은 축이고, 유니티에서 흔한 Newtonsoft.Json이라면 차이는 이보다 벌어집니다.
- 워밍업 1회 뒤에 재므로 파일은 OS 캐시에 있습니다 — 디스크 속도가 아니라 디코딩 비용을 재는 것이고, 그쪽이 기기가 바뀌어도 유지되는 비교입니다.
- 「로드 후 상주」는 로드 결과 한 벌만 살아 있는 상태에서 전체 GC 뒤의 관리 힙 증가분입니다. 로더 자신이 데워두는 것(직렬화기의 버퍼 풀과 메타데이터, JSON 쪽 약 3.5 MB)은 데이터에 청구하지 않고 따로 셉니다.

재현은 저장소 루트에서 세 줄입니다.

```
dotnet run --project src/SheetMan.csproj -- --recipe bench/recipe.jsonc
dotnet run --project bench/SheetMan.Bench.csproj -c Release -- verify bench/data
dotnet run --project bench/SheetMan.Bench.csproj -c Release -- binary bench/data 30
```

마지막 줄의 `binary` 자리에 `json`·`json-compact`·`sizes`를 넣으면 나머지가 나옵니다. 절대 수치는 기계를 타므로, 다른 기계에서는 배율을 보세요.
