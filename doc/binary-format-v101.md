# 바이너리 형식 v101 — 스키마 진화

> **상태: 계획. 아직 구현되지 않았습니다.** 이 문서가 승인되면 아래 단계 순서로 진행합니다.
>
> [문서 목록으로](../readme.md)

---

## 왜

현재 형식(v100)은 헤더가 `버전 + 예약바이트 + 행 수`뿐이고 그 뒤는 값만 이어집니다. 스키마가 파일에 없으므로 리더는 **생성 시점에 알던 순서대로** 읽습니다. 컬럼을 추가하든 지우든 순서를 바꾸든, 옛 리더는 첫 행에서 한 칸 밀리고 그 뒤 전부가 어긋납니다 — 실패가 아니라 **조용히 다른 값**이 됩니다.

클라이언트와 데이터를 **항상 함께 배포**한다면 문제가 없습니다. 문제는 라이브 서비스입니다:

- CDN에 데이터만 올려 패치하는 흐름 (readme가 이미 약속한 자동 패치가 이것입니다)
- 스토어 심사 중이거나 업데이트를 미룬 **구버전 클라이언트**가 새 데이터를 받는 경우
- 데이터만 롤백해서 **신버전 클라이언트**가 옛 데이터를 받는 경우

v101의 목표는 이 흐름에서 **어떤 스키마 변경도 조용한 오독으로 이어지지 않게** 하는 것입니다. 읽을 수 있으면 정확히 읽고, 읽을 수 없으면 컬럼 이름을 짚어 실패합니다.

## 레이아웃

핵심 결정: **행 지향이 아니라 컬럼 지향**입니다. 컬럼마다 데이터가 연속 블록이고 블록의 바이트 길이가 헤더에 있으므로, **모르는 컬럼 건너뛰기 = `advance(길이)` 한 번**입니다.

프로토버프처럼 값마다 태그를 달면 스키마 정보가 행 수만큼 반복됩니다. 정적 테이블의 행은 동종이라 그럴 이유가 없습니다 — 로컬라이제이션 20,000행 × 8칸 기준 값별 태그는 **156 KB**, 테이블 디스크립터는 **~50 B**입니다.

```
fixed32    version        = 101
fixed8     flags          = 0        (예약: 압축·암호화)
counter32  rowCount
counter32  columnCount
columnCount ×:                        ── 디스크립터 ──
  counter32  tag                      1 이상, 테이블 내 유일
  fixed8     wire                     하위 4비트 = 원소 타입, 5~6비트 = 종류, 7~8비트 = 예약(0)
  counter32  count                    스칼라 = 1, 고정배열 = N, 가변배열 = 0
  fixed32    byteLength               이 컬럼 블록의 총 바이트
columnCount ×:                        ── 데이터 ──
  블록: rowCount개의 값 (원소 인코딩은 v100과 동일)
```

**값 인코딩은 v100 그대로**입니다. 바뀌는 것은 배치(컬럼 지향)와 디스크립터뿐이므로, writer와 리더 13개의 값 읽기/쓰기 코드는 전부 재사용됩니다.

### 원소 타입 (wire 하위 4비트)

|값|원소|시트 타입|
|--|--|--|
|0|varint (지그재그)|`enum`|
|1|fixed8|`bool`|
|2|i32 (fixed32)|`int`, `foreign` 인덱스|
|3|i64 (fixed64)|`bigint`, `datetime`, `timespan`|
|4|f32 (fixed32)|`float`|
|5|f64 (fixed64)|`double`|
|6|string (counter32 길이 + UTF-8)|`string`|
|7|bytes16|`uuid`|
|8~15|예약||

i32와 f32는 크기가 같지만 **의미가 다르므로 구분**합니다. 구분하지 않으면 int→double 승격에서 비트 패턴을 잘못 해석합니다.

### 종류 (wire 5~6비트)

|값|종류|블록 내용|
|--|--|--|
|0|스칼라|rowCount개의 원소|
|1|고정 배열 (serial field)|rowCount × count개의 원소|
|2|가변 배열|행마다 `counter32 n` + n개의 원소|

가변 배열의 행별 길이도 블록 **안**이므로 byteLength가 전부 덮습니다 — 건너뛰기는 여전히 `advance` 하나입니다.

## 리더의 동작

로드 시작에 한 번 계획을 세우고, 행 루프의 비용은 오늘과 같습니다.

1. 헤더와 디스크립터를 읽는다.
2. 디스크립터마다 태그로 자기 멤버를 찾는다.
   - **모르는 태그** → `advance(byteLength)`. (신 데이터의 새 컬럼)
   - **아는 태그, wire 일치** → 블록을 그 멤버로 읽는다.
   - **아는 태그, wire 불일치** → 승격 표(아래)에 있으면 변환해 읽고, 없으면 **자기 필드 이름과 양쪽 타입을 짚어 실패**한다.
3. 파일에 없던 멤버 → 기본값. (구 데이터를 신 코드로)
4. 상호참조 해석은 오늘과 동일.

컬럼 순서는 계약이 아닙니다 — 태그가 식별합니다.

## 타입 변경: 방치하지 않고 두 지점에서 검사

“wire가 다르면 무조건 실패”는 위험을 리더에게 미루는 것입니다. 대신:

### 1. 리더의 승격 표 — 안전한 변환은 읽는다

수학적으로 무손실인 방향만, 언어마다 같은 표 하나로:

|파일의 원소|멤버의 원소|판정|근거|
|--|--|--|--|
|varint|i32|**읽음**|지그재그 해독이 곧 int32|
|varint|i64|**읽음**|위와 같음, 더 넓게|
|i32|i64|**읽음**|무손실 확장|
|f32|f64|**읽음**|무손실 확장|
|i32|f64|**읽음**|i32 전 범위가 f64에서 정확|
|그 외 전부|—|**이름 짚어 실패**|손실 가능성이 있으면 읽지 않음|

역방향(i64 파일 → i32 멤버 등)은 **절대 읽지 않습니다.** 잘릴 수 있는 값을 “대개는 맞겠지”로 읽는 것이 이 도구가 계속 없애온 실패 방식입니다.

이 표가 뜻하는 것: **타입을 넓히는 변경(int→bigint, float→double, enum→int)을 하면, 신 코드는 구 데이터를 그대로 읽습니다.** 데이터 롤백과 “클라이언트 먼저 업데이트” 순서가 안전해집니다.

### 2. 변환기의 베이스라인 검사 — 배포 전에 잡는다

승격 표가 못 지키는 방향이 하나 남습니다: **구 클라이언트가 넓어진 새 데이터를 받는 경우**(i64 파일 → i32 멤버). 이건 리더가 깨끗하게 실패하지만, 라이브에서는 그 “깨끗한 실패”도 장애입니다. 그래서 **변환 시점에** 잡습니다.

변환이 성공할 때마다 스키마 베이스라인(`<binary Path>/schema-baseline.json` — 테이블 → 태그 → wire·count)을 산출물로 남기고 커밋합니다. 다음 변환은 그것과 비교합니다:

|변경|판정|메시지|
|--|--|--|
|컬럼 추가 (새 태그)|통과|—|
|컬럼 삭제, `#이름@태그` tombstone 있음|통과|—|
|컬럼 삭제, tombstone 없음|**오류**|“시트에 `#이름@태그`로 남겨 태그를 예약하세요”|
|**태그 재사용** (지운 태그가 다른 wire로 재등장)|**오류, 우회 없음**|구버전이 새 데이터를 옛 필드로 읽는 유일한 경로. 절대 허용 안 함|
|타입 변경, 승격 표 방향|**오류, `AcceptSchemaChanges` 명시 시 통과**|“배포된 구버전 리더는 이 컬럼에서 이름을 짚어 실패합니다. 신 리더는 구 데이터를 읽습니다”|
|타입 변경, 그 외|**오류, 명시 시 통과**|양방향 모두 실패함을 경고|
|고정배열 count 변경|**오류**|“새 태그로 추가하거나 가변 배열을 쓰세요”|

베이스라인이 없으면(첫 실행) 만들기만 하고 검사하지 않습니다 — 비교 대상이 없는 것이지 위험이 아닙니다. 승인은 recipe의 `AcceptSchemaChanges: ["Item.Price"]`처럼 **컬럼 단위로 명시**합니다. 한 번 통과하면 베이스라인이 갱신되므로 승인 목록은 지워도 됩니다.

> 태그 배정을 락 파일에 맡기지 않는 이유: 락 파일이 없으면 조용히 다른 태그를 배정하는 실패가 생깁니다. 태그는 시트가 정하고(아래), 베이스라인은 **변경 감지에만** 씁니다 — 없으면 “비교 안 함”이지 “다르게 동작”이 아닙니다.

## 태그: 시트가 정한다

필드 이름 뒤에 `@N`을 붙입니다. 기존 문법(`*` 보조 인덱스, `#` 제외)과 합성됩니다.

```
index@1    Name@2    Price@3    #OldColor@4    *Grade@5    FutureUse@6
```

- 테이블 안에서 **전부 달거나 전부 안 달거나**입니다. 섞이면 오류 — 반쯤 단 표는 어느 쪽 보장도 못 합니다.
- `#이름@태그`는 모델에서 빠지지만 **태그는 예약**됩니다. 지운 컬럼의 tombstone이자, **미래를 위해 미리 잡아두는 자리**이기도 합니다.
- 태그를 안 달면 서수(1..N)가 태그가 됩니다. 형식은 하나(v101)로 유지되고 오늘과 동작이 같지만, **끝에 추가하는 것만 안전**합니다 — 중간 삽입은 서수가 밀려 태그가 바뀝니다. 검증기가 이 모드에서는 그렇게 경고합니다.
- 중복 태그, 0 이하는 오류.

## 라이브 서비스 시나리오 — 보장 요약

|시나리오|구 클라이언트 + 신 데이터|신 클라이언트 + 구 데이터|
|--|--|--|
|컬럼 추가|건너뜀, 정상 동작|기본값, 정상 동작|
|컬럼 삭제 (tombstone)|기본값, 정상 동작|건너뜀, 정상 동작|
|순서 변경 · 이름 변경|무관 (태그가 식별)|무관|
|타입 넓힘 (int→bigint 등)|**이름 짚어 실패** — 변환기가 배포 전에 승인 요구|**그대로 읽음** (승격 표)|
|그 외 타입 변경|이름 짚어 실패 — 변환기가 승인 요구|이름 짚어 실패|
|태그 재사용|**변환기가 원천 차단**|—|

어느 칸에도 “조용히 다른 값”이 없습니다. 그것이 이 설계의 불변식입니다.

## 왜 위험이 없는가 — 구조로

1. **기존 코드는 건드리지 않습니다.** 리더는 이미 읽고 있는 버전 정수로 분기합니다: 100 → 지금 그대로의 경로(무변경), 101 → 새 경로(추가). 회귀가 생길 자리가 없습니다.
2. **스킵에 타입별 로직이 없습니다.** 행 지향이었다면 “varint를 읽어 버리고, string은 길이만큼 넘기고…”를 13개 언어에 심어야 했고, 그 하나하나가 오독 서식지입니다. 컬럼 지향은 `advance(byteLength)` 하나입니다.
3. **언어별로 하나씩 착지합니다.** 각 언어는 자기 적합성 하네스(101)와 스큐 코퍼스(아래)를 통과할 때만 커밋됩니다.
4. **기본값 전환은 마지막입니다.** writer의 `FormatVersion` recipe 옵션은 13개 리더가 전부 착지할 때까지 100이 기본입니다. 어느 단계에서 멈춰도 아무것도 깨져 있지 않습니다.
5. **형식 골든.** 고정 워크북에서 쓴 v100·v101 파일을 바이트 그대로 커밋해두고 매 실행 비교합니다 — 형식이 실수로 움직이면 즉시 드러납니다.

## 검증 게이트

|게이트|무엇을 증명하나|
|--|--|
|기존 적합성 코퍼스 ×12 (v101로)|같은 스키마의 왕복이 v101에서도 정확|
|**스큐 코퍼스** ×12|`evolution-v1 / v2` 워크북 (태그 공유, 추가·삭제·순서·이름·타입변경·승격 케이스 전부 포함). v1 코드로 v2 데이터를, v2 코드로 v1 데이터를 읽어 기대값과 대조. 타입 불일치는 **이름을 짚어 실패하는지까지** 확인|
|형식 골든|v100·v101 바이트 고정|
|베이스라인 검사 테스트|표의 일곱 판정 각각 + 태그 재사용 차단 사보타주|
|태그 검증 테스트|중복·혼용·`#` 예약·서수 모드 경고|

스큐 코퍼스 없이 리더를 착지시키지 않습니다. 건너뛰기·승격은 “다른 바이트를 읽는” 새 경로이고, 그것이 적합성 코퍼스가 존재하는 이유인 실패 방식이기 때문입니다.

|5|시트 태그 `@N` + 검증, 베이스라인 검사, `AcceptSchemaChanges`|중|검증 테스트|

4단계가 가장 크지만 2·3단계에서 설계가 이미 증명된 뒤의 기계적 반복이고, 언어마다 독립적으로 되돌릴 수 있습니다.

## 부수 효과

- **TargetSide 스큐 내성**: 클라 리더가 서버 컷 파일을 받아도 구조적으로는 서버 전용 컬럼을 건너뜁니다 (목표는 아니지만 태그의 자연스러운 결과).
- **컬럼 단위 압축의 자리**: wire의 예약 비트와 헤더 flags가 있고, 컬럼이 연속 블록이라 v-next에서 싸게 붙습니다.
- readme의 자동 패치 약속(`Updater`)이 실제로 안전해지는 전제 조건이 갖춰집니다.

## 정한 것 (바꾸려면 말해주세요)

1. **컬럼 지향** — 스킵 위험 제거가 근거. 행 지향 + 타입별 스킵은 기각.
2. **태그는 시트의 `@N`** — 서수 폴백은 append-only임을 경고. 락 파일은 변경 감지 전용.
3. **승격 표는 무손실 5개만** — varint→i32/i64, i32→i64, f32→f64, i32→f64. 손실 가능성이 있으면 이름 짚어 실패.
4. **v100은 계속 읽음** — 리더의 기존 경로 무변경. writer 기본값 전환은 마지막.
5. **고정배열 count 변경은 비호환** — 새 태그로 추가하거나 가변 배열로.
