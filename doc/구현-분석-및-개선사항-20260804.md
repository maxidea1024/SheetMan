## 3. 결함

### 3-1. 값 조회가 실패하면 **빈 셀이 됩니다** — 높음

`src/History/HistoryStore.cs:547`

```csharp
private static object ValueId(IReadOnlyDictionary<string, long> values, string text)
    => text != null && values.TryGetValue(text, out long id) ? id : (object)DBNull.Value;
```

`text != null`인데 조회가 빗나가면 `DBNull`을 씁니다. 그런데 이 스키마에서 **`NULL`은 "모름"이 아니라 "셀이 비어 있었음"** 입니다. 조회에서 앞의 조건은 이미 `text != null`로 걸렀으므로, 뒤의 `DBNull`에 도달하는 유일한 경로는 **값이 있는데 id를 못 찾은 경우**뿐입니다.

결과: 리포트가 "이 셀이 값 X로 바뀌었다" 대신 **"이 셀이 비워졌다"** 고 말합니다. 조회는 전부 `LEFT JOIN value`(`HistoryQuery.cs:305,306,552,553`)라 NULL이 그대로 통과합니다. 실패하는 대신 값이 달라지는, 이 프로젝트가 정확히 방어하려는 그 형태입니다.

**한 줄로 고칩니다** — 조회가 빗나가면 던지십시오. `text == null`일 때만 `DBNull`입니다.

이게 왜 중요한가: 이 폴백은 `ResolveValues`가 절대 빗나가지 않는다는 전제에 의존하는데, 그 전제를 지키는 장치가 없습니다. 아래가 실제로 그 전제를 깨는 경로입니다.

### 3-2. 값 풀 GC의 락 범위가 주장과 다릅니다 — 중간

`src/History/HistorySchema.cs:49`의 주석:

> 그것[브랜치 쓰기 락]이 값 풀을 수거할 수 있게 해주는 것이기도 합니다. 이것이 없으면 prune이 변환이 값을 찾은 시점과 참조하는 시점 사이에서 값을 삭제할 수 있습니다.

그런데 락 이름은 `sheetman_history_write:{projectId}:{branch}`(`HistorySchema.cs:52`)로 **브랜치별**인데, `HistoryMaintenance.Collect`(`HistoryMaintenance.cs:212`)가 지우는 `value` 테이블은 **프로젝트·브랜치 전역 공유**입니다.

`main` 브랜치를 prune하는 동안 `dev` 브랜치(또는 다른 프로젝트)가 변환 중이면 두 프로세스는 **서로 다른 락**을 잡습니다. 워터마크는 GC 시작 이후 삽입된 값만 보호하고, 외래 키는 스키마에 **하나도 없습니다.**

이 창이 실제로 열리는지는 InnoDB의 중복키 잠금 동작(`INSERT IGNORE`가 기존 행에 S락을 거는지)에 달려 있는데, **코드는 그걸 주장하지도 검증하지도 않습니다.** 안전하다면 우연히 안전한 것입니다.

이게 §3-1과 만나면: GC가 지운 값을 변환이 못 찾고 → `DBNull` → 리포트에 빈 셀. 조용히.

**고치는 법** (택1)

- `cell_change.old_value_id` / `new_value_id` / `cell_current.value_id`에 **FK RESTRICT**. 삭제가 실패하고 그 값은 건너뜁니다. 가장 확실하지만 큰 테이블에 제약을 겁니다.
- `Collect`를 **전역 GC 락**으로 감싸고, `ResolveValues`도 같은 락을 짧게 잡습니다. 변환 간 동시성은 유지됩니다.
- 값 풀을 **프로젝트별로 분리**하고 락 범위를 맞춥니다. 중복 제거 효율이 조금 떨어집니다.

FK 쪽을 권합니다 — 데이터베이스가 불변식을 지키게 하는 편이, 주석이 지키게 하는 것보다 낫습니다. 지금 주석이 정확히 그 예입니다.

### 3-3. `--serve`가 오류를 삼킵니다 — 높음

`src/History/HistoryServer.cs`에는 예외 처리가 **없습니다.** `UseExceptionHandler`도, 핸들러 내부 `try`도 없습니다.

즉 잘못된 요청 하나가 **클라이언트에도 서버에도 아무 흔적을 남기지 않습니다.** CLI는 같은 상황에서 정확한 문장을 출력합니다. API와 CLI가 같은 답을 하도록 바이트 비교까지 하는 설계인데, **오류 경로만 그 대칭에서 빠져 있습니다.**

`HistoryServerTests`(286줄)도 성공·304·401만 확인하고 4xx/5xx 경로는 없습니다.

**고치는 법**: `SheetManException` → 400 + 메시지, 그 외 → 500 + 상관 ID로 매핑하는 미들웨어. Serilog를 `ILoggerProvider`로 다시 붙이거나, 최소한 미처리 예외만 Serilog로 흘리십시오. 테스트도 한 건 — 없는 커밋에 400과 그 안의 메시지.

### 3-4. Html 타깃이 **폐쇄된 CDN**을 참조합니다 — 중간

`src/templates/html-head.sbn:9-10`

```html
<link rel="stylesheet" href="https://stackpath.bootstrapcdn.com/bootstrap/4.3.1/css/bootstrap.min.css" ...>
<script src="https://stackpath.bootstrapcdn.com/bootstrap/4.3.1/js/bootstrap.min.js" ...></script>
```

세 가지가 겹칩니다.

3. **로컬 사본이 이미 있는데 안 씁니다.** `lib/bootstrap-4.3.1-dist/`가 커밋되어 있습니다. 참조하는 코드는 없습니다.

게이트가 못 잡은 이유는 정확합니다 — 골든 비교는 `<link>` 태그가 **committed된 것과 같은지**만 보지, 그 URL이 살아 있는지는 보지 않습니다.

**고치는 법**: `history.css`가 하는 것처럼 임베디드 리소스로 인라인하십시오. 히스토리 페이지가 이미 라이브러리 없이 SVG를 손으로 그리고 있으니, Html 타깃도 부트스트랩 없이 갈 수 있습니다. 그러면 `lib/bootstrap-4.3.1-dist/`도 지웁니다.

## 5. Unreal 타깃

### 5-1. 명명 규칙은 지켜지고 있습니다

`test/fixtures/output/unreal/Source/SheetManCore/Public/FSheetManCore.h` 실측:

| 관례 | 상태 |
|---|---|
| `E` 접두 (enum) | `EValueType` `EGrade` `ESkillType` ✔ |
| `F` 접두 (USTRUCT) | `FItemRow` `FTestFieldTypesRow` ✔ |
| `F` 접두 (일반 클래스) | `FItemTable` `FSheetManCore` ✔ |
| PascalCase 멤버 | `Index` `StringField` `DatetimeField` ✔ |
| PascalCase 함수 | `Read` `Find` `Records` `ReadAll` ✔ |
| `b` 접두 (bool) | `bBoolField` ✔ |
| UE 타입 | `FString` `FGuid` `FDateTime` `FTimespan` `TArray` `TMap` `int32` `int64` ✔ |
| API 매크로 | `SHEETMANCORE_API` ✔ |

`U`(UObject) · `A`(Actor)가 없는 것은 위반이 아니라 **그 둘을 만들지 않기 때문**입니다. 접두어 없는 snake_case는 일반 C++ 타깃(`OUT/cpp/A.h` — `struct TemplateRecord { std::int32_t index; }`)의 것이고, 그 언어에서는 그게 맞습니다.

### 5-2. 그런데 **리더는 Unreal 타깃이 아닙니다** — 높음

USTRUCT 층만 UE 규칙을 따르고, **그 아래 리더는 일반 C++ 타깃의 파일을 한 글자도 안 바꾸고 싣습니다.** `Public/SheetManLiteBinaryReader.h`:

```cpp
namespace sheetman {
class LiteBinaryError : public std::runtime_error { ... };
struct DateTime  { std::int64_t ticks = 0; };          // FDateTime 이 있는데
struct TimeSpan  { std::int64_t ticks = 0; };          // FTimespan 이 있는데
struct Uuid      { std::array<std::uint8_t,16> bytes;  // FGuid 가 있는데
                   std::string to_string() const; };
void read(std::string& value);                          // FString 이 있는데
```

그리고 그걸 되돌리려고 `unreal.sbn:36,48`이 어댑터를 답니다. 즉 **UE 타입 → 표준 C++ 타입 → 다시 UE 타입**입니다. 엔진에 이미 있는 것을 만들어서, 쓰고, 도로 버립니다.

생성된 `Private/FSheetManCore.cpp` 실측:

```cpp
{ std::string Temp{};       Reader.read(Temp); Name = SheetManConvert::ToString(Temp); }
{ sheetman::Uuid Temp{};    Reader.read(Temp); UuidField = SheetManConvert::ToGuid(Temp); }
```

셀당 비용:

| 타입 | 지금 | 있어야 할 것 |
|---|---|---|
| string | `std::string` 힙 할당 → `UTF8_TO_TCHAR` → `FString` 재할당·복사 = **할당 2회** | 버퍼에서 `FString`으로 직접 = 1회 |
| uuid | `Uuid` → `to_string()`(할당) → `FString`(할당) → **`FGuid::Parse` 텍스트 파싱** = 할당 3회 + 파싱 | 16바이트 → `FGuid` 직접 = 0회 |
| datetime | `sheetman::DateTime` → ticks → `FDateTime` | `FDateTime(Ticks)` 직접 |
| array | `std::vector` 경유 | `TArray` 직접 |

로컬라이제이션 테이블 하나가 메가바이트 단위라는 건 템플릿 자신이 적어둔 사실입니다(`unreal-cpp.sbn:86`). 그 규모에서 문자열마다 할당 두 번, uuid마다 텍스트 파싱 한 번은 그냥 낭비입니다.

### 5-3. 그리고 예외가 UE 모듈을 죽입니다 — **높음**

리더는 8곳에서 던집니다:

```cpp
throw LiteBinaryError("table data ended after " + std::to_string(position_) + " of " + ...);
throw LiteBinaryError("table format version ... is not supported");
throw LiteBinaryError("string length is negative");
```

그런데 생성된 `SheetManCore.Build.cs`는 **`bEnableExceptions`를 설정하지 않습니다.** Unreal은 C++ 모듈을 기본적으로 예외 비활성으로 빌드합니다.

더 나쁜 건 시그니처입니다:

```cpp
bool FItemTable::Read(const FString& Filename)   // ← bool 을 약속하는데
{
    ...
    const std::int32_t RowCount = sheetman::read_table_header(Reader);   // ← try/catch 없음
```

`unreal-cpp.sbn:76-105` 어디에도 `try`가 없습니다. 파일 열기 실패만 `false`를 반환하고(`:79-83`), **손상된 `.table`은 예외로 빠져나갑니다.** 예외가 꺼진 모듈에서는 그게 복구 가능한 실패가 아니라 종료입니다.

`bool`을 반환하는 함수가 지킬 수 없는 약속을 하고 있습니다.

### 5-4. 고치는 법 — Unreal 전용 리더

**엔진에 이미 있는 걸 쓰는 게 맞습니다.** 어댑터를 얹는 게 아니라 리더 자체를 UE 것으로 내야 합니다. UE 모듈 안에 표준 라이브러리 타입이 등장할 이유가 하나도 없습니다 — 전부 대응물이 있습니다.

| 지금 (표준 C++) | 써야 할 것 (엔진 제공) |
|---|---|
| `std::string` | **`FString`** |
| `std::vector<T>` | **`TArray<T>`** |
| `std::array<uint8,16>` + `sheetman::Uuid` | **`FGuid`** |
| `sheetman::DateTime` (ticks 래퍼) | **`FDateTime`** (.NET과 같은 100ns ticks) |
| `sheetman::TimeSpan` (ticks 래퍼) | **`FTimespan`** (동일) |
| `std::int32_t` `std::int64_t` `std::uint8_t` | **`int32` `int64` `uint8`** |
| `std::size_t` | **`int32`** |
| `std::runtime_error` 상속 예외 | **`bool` 반환 + 오류 상태** (§5-3) |
| `std::ifstream` | **`FFileHelper::LoadFileToArray`** (이미 상위에서 쓰고 있습니다) |

`FDateTime`·`FTimespan`이 특히 아깝습니다 — **둘 다 .NET과 동일한 100나노초 ticks**를 쓰기 때문에 `FDateTime(Ticks)` 한 줄이면 끝나는데, 지금은 같은 값을 담을 뿐인 구조체를 따로 정의해 두고 거쳐 갑니다.

`lib/unreal/sheetman/SheetManLiteBinaryReader.h`를 열한 번째 리더로 추가하십시오 — C++ 리더의 파생이 아니라 형제입니다.

```cpp
class FSheetManBinaryReader
{
public:
    explicit FSheetManBinaryReader(TArrayView<const uint8> Data);

    bool ReadString(FString& Out);              // 버퍼 → FString 직접, 중간 std::string 없음
    bool ReadGuid(FGuid& Out);                  // 16바이트 → FGuid 직접, 텍스트 파싱 없음
    bool ReadDateTime(FDateTime& Out);          // ticks → FDateTime(Ticks)
    bool ReadTimespan(FTimespan& Out);          // ticks → FTimespan(Ticks)
    bool ReadInt32(int32& Out);  ...

    bool HasError() const { return bFailed; }
    const FString& GetError() const { return Error; }
};
```

**예외 대신 `bool` + 오류 상태**입니다. UE의 관례이기도 하고, `Read()`가 이미 `bool`을 약속하고 있으니 그 약속을 실제로 지키게 됩니다.

바꿔야 할 것:

| 파일 | 변경 |
|---|---|
| `lib/unreal/sheetman/SheetManLiteBinaryReader.h` | **신규.** UE 타입 네이티브 리더 |
| `src/SheetMan.csproj` | 임베디드 리소스 한 줄 추가 |
| `src/templates/unreal.sbn` | `namespace SheetManConvert` **삭제** — 필요 없어짐 |
| `src/templates/unreal-cpp.sbn` | `Temp` 왕복 제거, `Reader.ReadX(Field)` 직접 호출 |
| `src/CodeGeneration/UnrealCodeGenerator.cs` | `temp_type` / `from_temp` 뷰 필드 제거, `read_call`이 UE 메서드를 가리키게 |

`.table` 와이어 포맷은 그대로이므로 **적합성 코퍼스가 그대로 적용됩니다** — 오히려 Unreal 리더가 코퍼스에 들어갈 수 있게 되어 §5-5의 공백도 같이 메워집니다. 지금은 C++ 리더를 재사용한다는 이유로 코퍼스 밖에 있는데, 전용 리더가 생기면 그 논리가 사라지기 때문입니다. (엔진 없이 컴파일할 수 없다는 제약은 남습니다 — `SHEETMAN_UE_ROOT`가 있을 때만 도는 게이트로 붙이십시오.)

작업량은 하루 정도로 봅니다. **§5-3(예외) 때문에 우선순위가 높습니다** — 지금은 손상된 데이터 파일 하나가 게임을 종료시킵니다.

### 5-5. 블루프린트에서 데이터에 닿을 수 없습니다 — 중간

`unreal.sbn:125`

```cpp
class SHEETMANCORE_API FSheetManCore   // UCLASS 아님
{
public:
    static const FItemTable& Item() { return ItemStorage; }   // UFUNCTION 아님
```

구조체는 전부 `USTRUCT(BlueprintType)`이고 프로퍼티도 `BlueprintReadOnly`인데, **접근자가 평범한 static C++ 클래스**입니다. 블루프린트에서 `FItemRow` 변수를 들 수는 있어도, **그걸 얻어올 방법이 없습니다.** C++ 코드를 거쳐야만 합니다.

`unreal.sbn:120-124`의 주석은 UObject를 안 쓰는 이유를 이렇게 답니다 — "데이터가 어떤 월드보다 오래 살고, 시작 시 한 번 읽고 변경되지 않으며, 리플렉션이나 GC가 필요 없다". 수명 관리 논리로는 옳습니다. 하지만 **리플렉션이 필요 없다는 부분은 틀렸습니다** — 모든 USTRUCT를 `BlueprintType`으로 내는 것 자체가 블루프린트 접근을 의도한 것인데, 그 의도가 마지막 한 걸음에서 끊깁니다.

**고치는 법**: 얇은 `UBlueprintFunctionLibrary`를 하나 더 내십시오. 소유권은 그대로 static 저장소에 두고, 테이블별로 `UFUNCTION(BlueprintPure)` 두 개(`GetItemRow(int32 Index, bool& bFound)` / `GetAllItemRows()`)만 감싸면 됩니다. GC도 월드 의존성도 생기지 않습니다.

### 5-6. Unreal은 적합성 코퍼스 밖에 있습니다 — 낮음

`UnrealTargetTests`(93줄)가 확인하는 것은 파일 존재, include 순서, uint8 범위, 그리고 `SHEETMAN_UE_ROOT`가 있을 때의 UHT 통과입니다. **읽은 값이 맞는지는 확인하지 않습니다.**

주석(`UnrealTargetTests.cs:13`)의 근거 — "와이어 포맷은 여기서 재구현하지 않는다, 모듈은 C++ 타깃과 같은 리더를 싣고 그건 이미 코퍼스로 검증된다" — 는 리더에 대해서는 맞습니다. 하지만 **`FSheetManCore.cpp`가 생성하는 `Read()` 본문**은 Unreal 전용이고, `ToString`/`ToGuid` 변환(`unreal.sbn:36,48`)도 Unreal 전용입니다. FGuid 바이트 순서가 어긋나도 UHT는 통과합니다.

UE 엔진 없이 검증할 방법이 마땅치 않다는 게 현실적 제약이라, **급하지 않지만 알려진 공백으로 기록**해 두는 게 맞습니다.

## 7. 저장소 위생 — 낮음

### 7-1. `OUT/` — 사고였지만 남길 값어치가 있습니다 ✅ **정식화 완료**

`c43c18e`(2026-08-03) 문서 작업 중 딸려 들어간 30개 파일이었고, 처음에는 지우자고 적었습니다. **철회합니다.**

이 트리는 `reserved-words` 픽스처를 **11개 언어 전부로 생성한 결과**이고, 회귀 스위트가 못 하는 일을 합니다 — 열한 개 제너레이터가 실제로 무엇을 뱉는지 **나란히, diff로** 보여줍니다. §5의 Unreal 문제를 찾아낸 것도 스위트가 아니라 이 트리였습니다. 게이트는 전부 초록이었으니까요.

그래서 재현 가능하게 만들었습니다:

```sh

```

`OUT/showcase.json`이 새로 들어갔고, 무엇을 왜 담는지 파일 안에 적혀 있습니다. **바이너리 익스포트는 뺐습니다** — 런타임 형식이고 골든 트리가 이미 덮으며, diff에서 읽을 수 없습니다. JSON과 Html은 남겼습니다.

재생성하자마자 이 방식의 값어치가 증명됐습니다 — 커밋되어 있던 `OUT/dart/a.dart`에 **이전에 고친 `int int = 0;` 버그가 그대로 남아 있었습니다.** 산출물을 커밋해두고 갱신하지 않으면 그 자체가 거짓말이 됩니다.

### 7-2. 저장소 루트의 산출물 — **실수가 아니라 버그였습니다** ✅ **조치 완료**

원인: `--new-recipe` 스켈레톤의 모든 엔트리는 `Path`가 빈 문자열이고, 제너레이터 12개 중 **`csharp`과 `typescript`에만 빈 Path 가드가 없었습니다.** `Path.Combine("", "GameData.cs")`는 아무것도 아닌 게 아니라 **상대 경로**라서, 두 타깃이 작업 디렉터리에 파일을 씁니다. `SourceRegistryTests`가 그 스켈레톤을 실제로 실행하므로, 테스트를 돌릴 때마다 저장소 루트가 오염됐습니다.

Html 타깃이 범인이던 시절에 쓰였고, **확장자 하나만 확인합니다.** 그래서 csharp·typescript는 계속 흘렸고 테스트는 계속 통과했습니다.
