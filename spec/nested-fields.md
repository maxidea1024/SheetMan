# 중첩 필드

> [문서 목록으로](../readme.md)

컬럼 여러 개를 **레코드 하나**, 또는 **레코드의 배열**로 접는 기능의 설계입니다.
왜 필요한지는 [uwo 레이아웃 분석](../doc/uwo-레이아웃-분석-20260808.md)에 있습니다.

---

## 1. 문제

지금 시트에서 배열을 만드는 방법은 둘이고, **둘 다 원소가 스칼라**입니다.

|방법|시트|나오는 것|
|--|--|--|
|serial field|`Text1` `Text2`|`string[]`, 길이 = 컬럼 수|
|배열 타입|`Costs` : `int[]`|`int[]`, 길이 = 로우마다|

원소가 여러 값을 묶은 것일 때 적을 방법이 없습니다. 실제 데이터에서 흔한 모양인데도
`Slot1Id` `Slot1Count` `Slot2Id` `Slot2Count`처럼 **평평하게 펼쳐 적고, 읽는 쪽에서 다시 묶는**
수밖에 없습니다. 생성된 코드가 시트의 의도와 다른 모양이 됩니다.

## 2. 표기 — `Group.Member`

**결정.** 멤버 이름을 `.`으로 붙이고, 배열은 **기존 연번 규칙을 그대로** 씁니다.

|시트의 컬럼 이름|나오는 것|
|--|--|
|`Pos.X` `Pos.Y`|`Pos` — 레코드 하나. `record.Pos.X`|
|`Slot1.Id` `Slot1.Count` `Slot2.Id` `Slot2.Count`|`Slot` — 레코드의 배열, 길이 2. `record.Slot[0].Id`|
|`Slot1` `Slot2`|스칼라 배열 (지금 그대로)|

타입·주석·target-side는 **멤버 컬럼마다 따로** 적습니다. 멤버는 서로 다른 타입일 수 있고,
그것이 레코드를 쓰는 이유입니다.

**왜 이 표기인가.**

- **연번 규칙을 새로 만들지 않습니다.** `Text1`/`Text2`를 이미 쓰는 사람이 `Slot1.Id`/`Slot2.Id`를
  적게 됩니다. 배열 길이를 컬럼 수가 정하는 것도, 그룹의 컬럼이 시트에서 붙어 있지 않아도 되는 것도
  [기존 폴딩](../src/Models/SerialField.cs)의 성질을 그대로 물려받습니다.
- **`.`은 지금 비어 있는 문법입니다.** 필드 이름은 [`RequiresIdentifier`](../src/Cooking/CookingContext.cs)를
  지나므로 `.`이 든 이름은 **현재 오류**입니다. 그래서 기존 시트와 모호해질 여지가 없습니다 —
  새 뜻을 얻는 것이 아니라 오류였던 것이 뜻을 갖습니다.
- **uwo 표기가 이 모델로 번역됩니다.** `character[0]["Id"]`는 `Character1.Id`와 같은 것을 가리키므로,
  uwo 레이아웃 파서는 **두 번째 모델이 아니라 번역**입니다. 모델이 하나면 두 레이아웃이
  「이 컬럼이 무엇인가」에 다른 답을 낼 수 없습니다.

**고르지 않은 것.**

|대안|왜 아닌가|
|--|--|
|`character[0]["Id"]` (uwo 그대로)|엑셀 헤더에 따옴표를 넣는 것이 편집에 불편하고, 인덱스 표기가 연번 규칙과 이중이 됩니다. 우리 레이아웃에는 이미 연번이 있습니다|
|`Slot[0].Id`|`.`만으로 충분한데 대괄호를 더합니다. 연번과 대괄호 둘 중 하나만 쓰는 게 낫고, 기존 규칙과 이어지는 쪽은 연번입니다|
|`Slot1_Id` (밑줄)|`_`는 이름 정규화에서 **지워집니다** — `Slot1_Id`와 `Slot1Id`가 같은 이름이 되므로 구분이 성립하지 않습니다|

## 3. 모델 — `SerialField`의 원소 타입을 넓힌다

익스포터와 13개 생성기가 보는 단위는 `Field`가 아니라
[`SerialField`](../src/Models/SerialField.cs) — 「컬럼들을 배열 하나로 접은 그룹」입니다.
중첩 필드는 **새 개념이 아니라 그 그룹의 원소가 스칼라에서 레코드로 넓어진 것**입니다.

```
SerialField
  Name         "Slot"
  Kind         Scalar | Record          ← 신규
  Members      [ { Name="Id", Fields=[Slot1.Id, Slot2.Id] },     ← 신규. Kind=Record일 때만
                 { Name="Count", Fields=[Slot1.Count, Slot2.Count] } ]
  Fields       (Kind=Scalar일 때 지금 그대로)
```

멤버 하나가 **원소 인덱스 순서의 `Field` 목록**을 들고, 그 목록의 길이가 배열 길이입니다.
`Pos.X`처럼 연번이 없으면 길이 1이고 배열이 아닌 레코드 하나로 냅니다.

## 4. 와이어 — 바꾸지 않습니다

컬럼 지향 형식이므로 **레코드의 배열은 「멤버마다 고정 배열 컬럼 하나」**입니다.

```
Slot1.Id  Slot2.Id     →  컬럼 Slot.Id     : KindFixedArray, 길이 2
Slot1.Cnt Slot2.Cnt    →  컬럼 Slot.Count  : KindFixedArray, 길이 2
```

즉 **API는 AoS, 파일은 SoA**입니다. 얻는 것이 셋입니다.

- `KindFixedArray`가 이미 그것이라 **형식에 새 kind가 없고, 버전을 올리지 않습니다.**
  스펙과 스큐 게이트가 그대로입니다.
- 멤버마다 별도 컬럼이라 [컬럼 인코딩](../doc/binary-format.md#컬럼-인코딩)이 멤버 단위로 걸립니다.
  같은 값이 이어지는 멤버는 런렝스가, 값 종류가 적은 멤버는 딕셔너리가 그대로 듣습니다.
  레코드를 한 덩어리로 저장하면 그 둘이 전부 무력해집니다.
- 멤버 추가가 **컬럼 태그 하나 늘는 가산적 변경**입니다. 기존 리더는 모르는 태그를 건너뜁니다.

`lib/`의 리더 13개도 그대로입니다. 생성되는 읽기 루프는 컬럼을 태그로 분기해
`record.<필드>[j]`에 대입하는 형태이고, 중첩은 **대입 대상이 `record.<그룹>[j].<멤버>`가
되는 것**이 전부입니다 — 디코드 원시연산은 건드리지 않습니다.

## 5. 지원하지 않는 모양

깊이 1까지입니다. 그룹의 멤버는 스칼라여야 하고, 멤버가 또 그룹일 수는 없습니다.

근거는 [실측](../doc/uwo-레이아웃-분석-20260808.md#실제로-쓰이는-중첩-모양은-셋뿐입니다)입니다 —
615개 테이블에서 **깊이 1의 세 모양이 리프의 99.5%**이고, 더 깊은 것은 8개뿐입니다.
1%도 안 되는 모양 때문에 재귀 일반화를 먼저 할 이유가 없습니다.
필요해지면 `Members`가 `SerialField`를 담게 넓히는 방향이고, 그때까지는 **명시적 오류**입니다.

「배열의 배열」도 같습니다. [지금도 거부](../src/Models/Table.cs)하는 모양이라 판단이 이미 서 있습니다.

## 6. 단계 — 언어를 하나씩

13개 템플릿을 한 번에 고치지 않습니다. 중첩을 아직 모르는 타깃은 **그 사실을 말하는 오류**를
내게 하고, 언어를 하나씩 늘립니다.

```
Target `go` does not support nested fields yet.
  Table `Item` field `Slot` is a record group.
  at sheets/data.xlsx : Items : F3
```

조용히 평평하게 펼치는 것보다 낫습니다 — 그러면 13개 산출물 중 하나만 다른 모양이 되고,
어느 것이 맞는지 아무도 모릅니다.

|단계|내용|
|--|--|
|1|이름 파싱 (`Group.Member` → 그룹·멤버·연번). 순수 함수, 단위 테스트|
|2|모델 (`SerialField.Kind`·`Members`) 과 폴딩|
|3|픽스처 워크북 + C# 생성기 + JSON 익스포터. **여기서 끝까지 한 번 돌아갑니다**|
|4|나머지 12개 언어. 하나씩, 적합성 코퍼스에 모양 추가|
|5|HTML·DB 익스포터, 쇼케이스 재생성|
|6|`uwo` 레이아웃 파서에서 이 모델로 번역|
